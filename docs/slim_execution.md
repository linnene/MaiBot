## 为什么先做按需加载

源码审查发现三个实际入口：mcp_module 包初始化、进程级 service、WebUI MCP 路由都曾主动导入连接实现。只改其中一个入口无法解除加载。

相反，模型客户端已按配置加载，因此不能把“删除 Gemini 客户端”当作已证实可节省当前内存的办法。表达向量总开关与热更新也应保留，不能因为暂时关闭就切断 embedding。

## 证据

独立解释器导入 MCP service 与 WebUI MCP 路由的单次探索性测量，环境均为本机既有 Python 3.12.14：

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| MCP SDK 已加载 | 是 | 否 |
| sys.modules 项数 | 1771 | 823 |
| 导入耗时 | 0.658 秒 | 0.380 秒 |
| 进程峰值 RSS | 132.7 MiB | 97.3 MiB |

这是**局部导入实验、各一次采样**，不是生产进程的节省量，不能据此声称线上 RSS 从基线减少了相同数值。收益还须在实际部署与同等流量下测量。

MCP 配置、连接、共享服务、WebUI 连接测试及新增的独立解释器不加载断言共 20 项测试通过。所有测试均使用合成配置或模拟连接，不访问真实 MCP 服务、不调用外部模型。

## 上线复测与第二批优化

前后各约一分钟、每五秒采一次的同口径自然空闲观测，两个窗口均无模型调用，窗口内配置未变：

| 指标 | MCP 上线前 | MCP 上线后 |
| --- | ---: | ---: |
| 进程组 RSS 平均 | 618.34 MiB | 610.45 MiB |
| CPU 平均（一个核百分比） | 0.962% | 0.915% |

这是顺序采样、期间发生过重启，不能隔离缓存、进程预热和自然波动；RSS 变化约 7.89 MiB，不沿用上面的局部导入实验作为生产节省量，也不把 CPU 差异当成已证实收益。原始 cgroup 计数也保留在证据中，但不与进程组 RSS 混用。

遥测此前虽然关闭上传，启动仍导入实现并创建每 600 秒、11451 秒运行的两个任务。现在通过轻量生命周期服务收口，上传任务与依赖只在启用时加载，监听仍保留。本优化没有删除上传功能，也没有改任何部署开关。

补充的 MCP 冷进程测试覆盖首次启用、sampling bridge、配置复用、停用和关闭，模块导入与建连线程边界也有断言。与遥测及真实信号退出合计 **102 项通过、0 跳过**；遥测另在服务器 Python 3.13 用内存配置完成停用烟测。

联合验证发现原有退出确认 fixture 未注入 resource_path，七个测试先于遥测初始化就失败；未改动代码的 HEAD 隔离对照亦复现。补齐夹具后完整联合测试通过，不修改产品协议确认流程。固定瘦身结构集合仍保留原来的 14 项失败，不跳过或改名掩盖。

线上启动文件与本地有诊断逻辑差异，因此只应用生命周期小补丁，未整文件覆盖或重置工作树。两批均有独立源码备份；重启后检查本次 systemd invocation、WebUI HTTP 和向量通道，未把旧失败日志混入当前启动结论。
